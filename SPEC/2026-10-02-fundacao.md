# Spec: Fundação do projeto

- **Data:** 2026-10-02
- **Componente:** fundacao
- **Status:** aprovada para implementação
- **Substitui:** nenhuma

## O quê

Criar a base técnica do **Filme Certo**, um sistema web de recomendação individual de filmes. A base reimplementa e melhora o antigo MovieMatch.

Esta spec entrega um projeto Next.js vazio de funcionalidades de negócio, mas pronto para receber as próximas specs. Ele já vem com:

- estrutura de pastas;
- design system;
- clientes do Supabase;
- validação de variáveis de ambiente;
- testes configurados;
- CI;
- layout base com a atribuição obrigatória ao TMDB;
- deploy na Vercel.

## Por quê

O projeto antigo não tinha testes, schema versionado, configuração de deploy nem validação de ambiente. Por isso, erros simples, como a falta da variável `PORT` ou um `.env.example` com nome errado, só apareciam em produção.

Criar a fundação primeiro garante três coisas:

- toda funcionalidade seguinte já nasce testável;
- toda funcionalidade é verificada no CI;
- toda funcionalidade é publicada na URL pública que a AP1 exige.

## Decisões técnicas

| Tema | Decisão |
|---|---|
| Framework | Next.js na última versão estável, com App Router, em `src/app` |
| Linguagem | TypeScript com `strict: true` |
| Gerenciador de pacotes | pnpm |
| Estilo | Tailwind CSS + shadcn/ui; tema escuro como padrão |
| Banco/Auth | Supabase via `@supabase/ssr` (clientes para server, browser e middleware) |
| CLI do banco | `supabase` como devDependency; pasta `supabase/` com `config.toml` e `migrations/` vazia |
| Validação | zod |
| Testes unitários/componentes | Vitest + Testing Library + jsdom |
| Testes E2E | Playwright |
| Qualidade | ESLint e Prettier |
| CI | GitHub Actions |
| Deploy | Vercel, ligada ao repositório GitHub |

### Estrutura de pastas

```
src/
  app/                 rotas (App Router)
  components/ui/       componentes do design system (shadcn/ui)
  components/layout/   header, footer
  features/            uma pasta por domínio (vazia nesta spec)
  lib/
    env.ts             validação das variáveis de ambiente
    supabase/          server.ts, client.ts, middleware.ts
tests/
  unit/
  e2e/
supabase/
  config.toml
  migrations/
```

### Variáveis de ambiente

| Variável | Onde é usada | Obrigatória |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | servidor e navegador | sim |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | servidor e navegador | sim |
| `TMDB_READ_TOKEN` | **somente servidor** | sim |

- `src/lib/env.ts` valida as variáveis com zod no primeiro acesso.
- O `TMDB_READ_TOKEN` fica num módulo `server-only`, então nunca é empacotado para o navegador.
- O arquivo `.env.example` lista todas as variáveis, sem valores reais.

### Layout e atribuição

- **Header:** mostra a marca "Filme Certo".
- **Footer:** mostra o logo do TMDB, menor que a marca, e o aviso exato:
  > This product uses the TMDB API but is not endorsed or certified by TMDB.
- **Página `/sobre`:** descreve o projeto e repete a atribuição ao TMDB. Também informa que os dados de "onde assistir" são fornecidos pela **JustWatch**.
- **Imagens:** `next.config` libera imagens remotas de `image.tmdb.org`.

### Rotas desta spec

- `/`: página inicial provisória com a marca e um texto de apresentação. A spec de auth vai mudar essa rota.
- `/sobre`: créditos e atribuições.
- `GET /api/health`: responde `200` com `{ "status": "ok" }`.

## Critérios de aceitação

1. `pnpm install` seguido de `pnpm build` termina sem erros.
2. `pnpm lint` e `pnpm typecheck` (`tsc --noEmit`) terminam com zero erros.
3. `pnpm test` roda o Vitest, e passam pelo menos estes testes:
   - `env.ts` lança um erro **que cita o nome da variável** quando uma variável obrigatória está faltando;
   - `env.ts` retorna os valores tipados quando todas as variáveis estão presentes;
   - o componente Footer mostra o texto exato da atribuição ao TMDB.
4. `pnpm test:e2e` roda o Playwright, e passam estes testes:
   - `/` mostra "Filme Certo";
   - `/sobre` mostra a atribuição ao TMDB e a menção à JustWatch;
   - `GET /api/health` responde `200` com `{ "status": "ok" }`.
5. O `TMDB_READ_TOKEN` não aparece em nenhum arquivo de `.next/static` depois do build. O teste é um `grep` no build.
6. O `.gitignore` ignora `.env*`, exceto `.env.example`. Nenhum arquivo `.env` com valores reais é commitado.
7. O workflow do GitHub Actions roda lint, typecheck e testes unitários a cada push e pull request, e passa na branch `main`.
8. A aplicação está publicada na Vercel, e a URL pública consta no `README.md` como link clicável.
9. O `README.md` tem todas as seções exigidas pela AP1:
   - URL;
   - nomes da dupla;
   - stack;
   - como rodar;
   - ferramentas e modelos de IA usados;
   - saída do `cloc`.

   Seções sem conteúdo ainda podem ficar marcadas para serem completadas nas próximas specs.
10. As pastas `SPEC/`, `src/`, `tests/` e `prompts/sessoes/` existem na raiz.

## Fora do escopo

- Tabelas, migrations com conteúdo e políticas RLS. Elas entram nas specs de auth e de dados do usuário.
- Cadastro, login e proteção de rotas (spec `auth`).
- Cliente da TMDB e qualquer chamada à API (spec `cliente-tmdb`).
- Telas de negócio: dashboard, detalhes, busca, listas e perfil.
- Alternância entre tema claro e escuro. Só o tema escuro é entregue agora; a troca fica para a spec `extras`.
- Internacionalização. A interface é só em pt-BR.
