# Spec: Autenticação

- **Data:** 2026-10-02
- **Componente:** auth
- **Status:** aprovada para implementação
- **Substitui:** nenhuma

## O quê

Permitir que uma pessoa crie uma conta no **Filme Certo**, entre, saia e acesse áreas protegidas. A autenticação usa o **Supabase Auth** com email e senha.

Esta spec entrega:

- telas de cadastro e de login;
- logout;
- a tabela `perfis`, criada automaticamente no cadastro, protegida por RLS;
- a proteção das rotas da área logada;
- uma página `/dashboard` provisória, que a spec `dashboard` vai substituir;
- testes de integração e E2E rodando contra um Supabase local em Docker, também no CI.

## Por quê

O MovieMatch antigo tinha autenticação própria com JWT e bcrypt e acumulava problemas de segurança:

- o filtro `.or()` do login podia ser manipulado pelo texto digitado;
- o cadastro não era transacional e deixava registros órfãos, impedindo o mesmo email de se cadastrar de novo;
- a senha aparecia no `console.log` do navegador;
- o formulário aceitava campos vazios.

O Supabase Auth resolve a gestão de senhas e sessões. O trigger no banco cria o perfil na mesma transação do usuário, e a RLS garante no próprio Postgres que cada pessoa só enxerga os próprios dados. Todas as próximas specs (preferências, avaliações, listas) dependem de um usuário autenticado e de `auth.uid()` nas políticas.

## Decisões técnicas

| Tema | Decisão |
|---|---|
| Provedor | Supabase Auth, só email e senha |
| Confirmação de email | **Desligada** no projeto Supabase: cadastrou, entrou |
| Sessão | Cookies via `@supabase/ssr`, renovados por `src/proxy.ts` |
| Formulários | Server Actions com `useActionState`; o mesmo schema zod valida no cliente e no servidor |
| Perfil | Tabela `public.perfis`, criada por trigger em `auth.users` |
| Autorização | RLS no Postgres; o proxy é só uma checagem otimista e o layout da área logada confere de novo |
| Testes de banco | Supabase local (`supabase start`, Docker), também no CI |

### Rotas

| Rota | Acesso | Comportamento |
|---|---|---|
| `/` | público | Landing. Sem sessão: botões **Entrar** e **Criar conta**. Com sessão: redireciona para `/dashboard`. |
| `/cadastro` | só sem sessão | Formulário com nome, email, senha e confirmação de senha. |
| `/login` | só sem sessão | Formulário com email e senha. Aceita `?next=<caminho>`. |
| `/dashboard` | só com sessão | Página provisória com "Olá, {nome}". Fica no grupo de rotas `(app)`. |
| `/sobre` | público | Sem mudança. |

O logout é uma Server Action chamada pelo botão **Sair** do header, que encerra a sessão e leva para `/`.

### Proteção de rotas

1. `src/proxy.ts` chama `updateSession` (`src/lib/supabase/middleware.ts`) em toda requisição de página, exceto arquivos estáticos e imagens. Ele renova o cookie da sessão e redireciona:
   - quem não tem sessão e abre uma rota de `(app)` vai para `/login?next=<rota>`;
   - quem tem sessão e abre `/login` ou `/cadastro` vai para `/dashboard`.
2. O layout de `src/app/(app)/` chama `getUser()` no servidor e redireciona para `/login` se não houver usuário. A documentação do Next.js 16 diz que o proxy não deve ser a única barreira.
3. O parâmetro `next` passa por `sanitizarNext`. Só caminhos internos que começam com uma única `/` são aceitos. Qualquer outro valor (`//evil.com`, `https://…`, `/\evil.com`, vazio) vira `/dashboard`.

### Formulários e mensagens

Schema em `src/features/auth/schema.ts`:

| Campo | Regra | Mensagem |
|---|---|---|
| `nome` | 2 a 50 caracteres, depois de remover espaços das pontas | "Informe um nome entre 2 e 50 caracteres." |
| `email` | email válido | "Informe um email válido." |
| `senha` | mínimo de 8 caracteres, com pelo menos uma letra e um número | "A senha precisa ter ao menos 8 caracteres, com letras e números." |
| `confirmacao` | igual a `senha` | "As senhas não conferem." |

No login, a senha só precisa estar preenchida ("Informe sua senha."). As regras de força valem só no cadastro.

Os erros do Supabase são traduzidos por `traduzirErroAuth`:

| Erro do Supabase | Mensagem ao usuário |
|---|---|
| `invalid_credentials` | "Email ou senha incorretos." |
| `user_already_exists` / `email_exists` | "Este email já está cadastrado." |
| `weak_password` | "A senha precisa ter ao menos 8 caracteres, com letras e números." |
| `over_request_rate_limit` / `over_email_send_rate_limit` | "Muitas tentativas. Aguarde um pouco e tente de novo." |
| qualquer outro | "Não foi possível concluir agora. Tente de novo." |

A mensagem original do Supabase vai só para o log do servidor, nunca para a tela.

Acessibilidade: todo campo tem `label`; os erros ficam ligados ao campo por `aria-describedby` e o campo recebe `aria-invalid`; o botão de envio fica desabilitado e mostra "Entrando…" ou "Criando conta…" durante o envio. Os valores digitados (exceto senhas) são mantidos quando a validação falha.

O header mostra o nome do usuário e o botão **Sair** quando há sessão, e os links **Entrar** e **Criar conta** quando não há.

### Banco de dados

Migration `supabase/migrations/<timestamp>_auth_perfis.sql`:

- **Tabela `public.perfis`**
  - `id uuid primary key references auth.users(id) on delete cascade`
  - `nome text not null check (char_length(nome) between 2 and 50)`
  - `criado_em timestamptz not null default now()`
  - `atualizado_em timestamptz not null default now()`
- **Função `public.criar_perfil()`**: `security definer`, `set search_path = ''`. Insere em `public.perfis` o `id` do novo usuário e o `nome` de `raw_user_meta_data ->> 'nome'`, com espaços das pontas removidos.
- **Trigger** `after insert on auth.users for each row` que chama `public.criar_perfil()`. O cadastro envia o nome em `options.data.nome` no `signUp`. Se o nome for inválido, o `check` falha e o próprio usuário não é criado, porque tudo roda na mesma transação.
- **Trigger** `before update on public.perfis` que atualiza `atualizado_em`.
- **RLS ligada** em `public.perfis`, com as políticas:
  - `select` para `authenticated` quando `id = (select auth.uid())`;
  - `update` para `authenticated` quando `id = (select auth.uid())`, tanto em `using` quanto em `with check`.
  - Nenhuma política de `insert` ou `delete`: só o trigger cria perfis, e a exclusão acontece em cascata.

Os tipos do banco são gerados com `supabase gen types typescript --local` em `src/lib/supabase/database.types.ts`, e os três clientes Supabase passam a ser tipados com eles.

### Variáveis de ambiente

Nenhuma nova. O auth usa só `NEXT_PUBLIC_SUPABASE_URL` e `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`. A chave `service_role` **não** é usada.

### Testes e CI

- **Vitest** ganha dois projetos: `unit` (`tests/unit/`, jsdom, sem rede) e `integration` (`tests/integration/`, node, contra o Supabase local). `pnpm test` roda só `unit`; `pnpm test:integration` roda `integration`.
- Os testes de integração e o E2E leem a URL e a publishable key do Supabase local. São valores públicos e fixos do ambiente de desenvolvimento, não segredos.
- O workflow do GitHub Actions instala a CLI com `supabase/setup-cli`, roda `supabase start` (que aplica as migrations) e então executa lint, typecheck, testes unitários, testes de integração, build, `check:secrets` e E2E.
- Cada teste E2E e de integração cria seus usuários com email aleatório, para os testes não dependerem uns dos outros.

### Produção

No README, em "Como rodar", entram os passos para o projeto Supabase de produção:

1. desligar **Confirm email** em Authentication → Sign In / Providers → Email;
2. `pnpm exec supabase link --project-ref <ref>`;
3. `pnpm exec supabase db push`, que aplica as migrations.

## Critérios de aceitação

1. `supabase start` aplica a migration sem erros, e `supabase db reset` a reaplica do zero sem erros.
2. **Testes unitários** (`pnpm test`) passam, cobrindo pelo menos:
   - o schema de cadastro aceita dados válidos e rejeita, com a mensagem da tabela, nome curto, email inválido, senha sem número, senha curta e confirmação diferente;
   - `sanitizarNext` aceita `/filme/1` e `/dashboard?x=1` e devolve `/dashboard` para `//evil.com`, `https://evil.com`, `/\evil.com`, `evil` e valor ausente;
   - `traduzirErroAuth` devolve a mensagem da tabela para cada código listado e a mensagem genérica para um código desconhecido;
   - o formulário de cadastro mostra a mensagem de erro do campo e marca o campo com `aria-invalid`.
3. **Testes de integração** (`pnpm test:integration`, Supabase local) passam, provando que:
   - `signUp` com `nome` cria a linha em `perfis` com o mesmo `id` do usuário e o nome sem espaços nas pontas;
   - `signUp` com nome de 1 caractere falha e nenhum usuário é criado;
   - o usuário A lê o próprio perfil;
   - o usuário A recebe zero linhas ao ler o perfil de B;
   - o `update` do usuário A no perfil de B não altera nada;
   - o usuário A não consegue inserir uma linha em `perfis`;
   - um visitante sem sessão recebe zero linhas ao ler `perfis`.
4. **Testes E2E** (`pnpm test:e2e`, Supabase local) passam, cobrindo:
   - cadastro com dados válidos leva a `/dashboard`, que mostra "Olá, {nome}";
   - cadastro com email já usado mostra "Este email já está cadastrado.";
   - **Sair** leva a `/`, e depois disso `/dashboard` redireciona para `/login?next=%2Fdashboard`;
   - login com senha errada mostra "Email ou senha incorretos.";
   - login a partir de `/login?next=%2Fdashboard` leva a `/dashboard`;
   - com sessão, abrir `/login`, `/cadastro` ou `/` leva a `/dashboard`;
   - os testes E2E da fundação continuam passando.
5. Nenhuma senha aparece em `console.log`, nas respostas das Server Actions ou nos logs do servidor.
6. `pnpm lint`, `pnpm typecheck`, `pnpm build` e `pnpm check:secrets` terminam sem erros.
7. O workflow do GitHub Actions roda os testes unitários, de integração e E2E contra o Supabase local e passa na branch `main`.
8. A migration foi aplicada no projeto Supabase de produção, e na URL da Vercel é possível criar conta, ver "Olá, {nome}", sair e entrar de novo.
9. O README descreve como subir o Supabase local (`supabase start`), rodar os testes de integração e aplicar as migrations em produção.

## Fora do escopo

- Recuperação de senha ("esqueci minha senha") e troca de senha.
- Confirmação de email e configuração de SMTP próprio.
- Login social (Google, GitHub etc.) e login por link mágico.
- Edição de nome e avatar (spec `perfil`).
- Exclusão de conta.
- Onboarding de preferências e o redirecionamento para ele (spec `onboarding-preferencias`).
- Conteúdo real do dashboard (spec `dashboard`).
- Limitação de tentativas além da que o próprio Supabase Auth já faz.
